<div class="px">
<header class="hero">
<div class="kicker">Probabilistic data structures — membership in a handful of bits</div>
<p class="lede">A Bloom filter answers one question — <strong>“have I seen this before?”</strong> — using a bit array far too small to store the items themselves. It never misses an item that was inserted, and it sometimes cries wolf: a false positive. That trade, a tiny memory footprint in exchange for a controllable error rate, makes it one of the most deployed ideas in systems software, from database engines to network routers.</p>
<div class="keybox"><p><strong>The one-sentence idea.</strong> Hash each item with k different hash functions and set those k bits in an m-bit array. To query, check the same k bits: if any is 0 the item is <em>definitely absent</em>; if all are 1 it is <em>probably present</em> — the bits may have been set by other items. No false negatives, ever; false positives at a rate you choose when you size the filter.</p></div>
</header>
</div>

## 1 — How it works: k hashes, m bits, nothing else stored

<div class="px">
<p>Burton Bloom described the structure in 1970. It has exactly two ingredients: a bit array of m bits, all initially 0, and k hash functions that each map an item to a position in the array. Nothing about the item itself is stored — no key, no pointer, no copy. The array <em>is</em> the whole data structure, which is why it is so small.</p>

<h3>How to read this</h3>
<ul>
<li><strong>A 0 bit is proof.</strong> If a query finds any of its k bits at 0, the item cannot have been inserted — inserting it would have set that bit, and bits are never cleared.</li>
<li><strong>All 1s is only a hint.</strong> The k bits may belong to k different other items. The filter cannot tell who set a bit.</li>
<li><strong>Collisions are the mechanism, not a bug.</strong> With 5 items × 3 hashes in 32 bits, the five fruits set 15 distinct bits — nearly half the array — so collisions are already likely. Step 2 quantifies exactly how likely.</li>
</ul></div>

## 2 — False positives: the price, and how it grows

<div class="px">
<p>Why can there never be a false negative? A query for an inserted item checks bits that its own insertion set to 1, and in a standard Bloom filter bits never go back to 0. The answer for a true member is therefore always “present”. The error is one-sided by construction.</p>
<p>A false positive needs a conspiracy: every one of the query’s k bits was set by <em>someone else</em>. The more items inserted, the larger the fraction of bits set — the <em>fill</em> — and the easier that conspiracy becomes. After inserting n items, the probability that a given bit is still 0, and the resulting false-positive probability, are:</p>

## 3 — Sizing math: pick p, get m and k

<div class="px">
<p>In practice you design backwards: you know roughly how many items n the filter must hold, and the false-positive rate p you can tolerate. Two formulas then fix the array size m and the hash count k. The derivation of the optimal k is short enough to do in full — and the key step is kept explicit, because the result (aim for a half-full array) is the most useful intuition in this whole page.</p>

## 4 — Counting Bloom filter: buying deletion with counters

<div class="px">
<p>The standard filter cannot delete: a bit may be shared by several items, so clearing it on one item’s removal could evict others — creating false <em>negatives</em>, the one thing the structure promises never to do. The counting Bloom filter (Fan et al., 2000) replaces each bit with a small counter, typically 4 bits. Insert increments the k counters; delete decrements them; a query asks whether all k counters are above 0. An item can leave when its counters are no longer needed by anyone else.</p>

<div class="readbox">
<h3>What the counters cost, and their limit</h3>
<ul>
<li><strong>4× the memory</strong> of a plain filter at the same m (4-bit counters instead of 1-bit flags) — or, at fixed memory, an m four times smaller and a higher p.</li>
<li><strong>Counters can overflow.</strong> With 4-bit counters the ceiling is 15; Fan et al. showed that for typical sizing the chance any counter overflows is tiny, but implementations must still choose a policy (saturate, or size up) — a saturated counter can no longer be decremented safely.</li>
<li><strong>Deletion must be truthful.</strong> Decrementing for an item that was never inserted — or was only a false positive — steals counts from real members and can manufacture false negatives.</li>
</ul></div>
</div>

## 5 — Variants: one idea, many shapes

<div class="px">
<p>Almost every limitation of the 1970 design has a named descendant. The table compares the main ones on the axes that actually decide deployments: whether items can leave, whether the set can grow, and what the structure pays for it.</p>
<table class="data">
<tr><th>Variant</th><th>Change from the classic filter</th><th>Gains</th><th>Pays</th></tr>
<tr><td><strong>Counting Bloom</strong> (2000)</td><td>Bits become small counters</td><td>Deletion</td><td>≈4× memory at the same m</td></tr>
<tr><td><strong>Scalable Bloom</strong> (Almeida et al., 2007)</td><td>A chain of filters with growing m and tightening p; a new filter is appended when one fills</td><td>Set can grow without knowing n in advance; total p stays bounded</td><td>Queries check every filter in the chain</td></tr>
<tr><td><strong>Compressed Bloom</strong> (Mitzenmacher, 2001)</td><td>Optimised for sending the filter over a network: size it larger than memory-optimal and compress for transmission</td><td>Fewer transmitted bits per query answered at the receiver</td><td>Larger uncompressed array at rest</td></tr>
<tr><td><strong>Blocked Bloom</strong></td><td>Array split into cache-line-sized blocks; all k hashes of an item land in one block</td><td>One cache miss per lookup instead of k — the variant most large in-memory systems actually run</td><td>Slightly higher p for the same m, because hashes are confined to a block</td></tr>
<tr><td><strong>Quotient filter</strong> (Bender et al., 2011)</td><td>Stores a compact fingerprint of each hash inside a hash-table-like array, not just presence bits</td><td>Deletion, resizing, and merging; sequential scans are cache-friendly</td><td>More complex bookkeeping; fingerprints, not raw bits, set the error rate</td></tr>
<tr><td><strong>Cuckoo filter</strong> (Fan et al., 2014)</td><td>Cuckoo hashing over short fingerprints, with partial-key relocation</td><td>Deletion, and better space than Bloom once p drops below roughly 3%; lookups touch two buckets</td><td>Inserts can fail near full load and may need a stash or a rebuild</td></tr>
</table>
<div class="callout"><p><strong>Choosing, in one breath.</strong> Fixed known n and no deletion: classic (usually blocked) Bloom. Deletion needed: counting Bloom, or a cuckoo filter when p must be low. Unknown or growing n: scalable Bloom, or a quotient filter if you also need merges and resizes. The classic design remains the default because its query is a handful of bit tests with zero bookkeeping.</p></div>
</div>

## 6 — Applications: a cheap “no” that saves expensive work

<div class="px">
<p>Every deployment has the same shape: an expensive operation — a disk read, a decompression, a network round trip — guarded by a filter whose “definitely not” lets the system skip the work entirely. A false positive merely wastes one expensive check; a false negative would lose data, so the one-sided error is exactly the right way round.</p>
<div class="appgrid">
<div class="appcard">
<span class="tag tag-teal">Caching</span><h3>Cache digests &amp; admission</h3>
<ul>
<li><strong>Web cache digests:</strong> proxy caches such as Squid exchange Bloom-filter digests of what they hold, so a peer is only queried when the digest says “probably here” — turning an all-peers broadcast into a directed request.</li>
<li><strong>CDN and browser caches:</strong> a compact summary of a remote cache’s contents avoids fetching objects the edge cache provably does not have.</li>
<li><strong>Cache admission:</strong> “have we seen this key before?” filters keep one-hit wonders out of the cache — an item is admitted only on its second appearance, which the filter can attest cheaply.</li>
</ul></div>
<div class="appcard">
<span class="tag tag-orange">Databases</span><h3>Skipping disk reads in LSM stores</h3>
<ul>
<li><strong>LSM-tree SSTables:</strong> LevelDB, RocksDB, Apache Cassandra and HBase keep a Bloom filter per data file. A point lookup checks the filter first; a “no” skips opening that file at all. With data spread over many files, this is the difference between one disk read and dozens.</li>
<li><strong>Join and dedup guards:</strong> a filter over the keys already seen cheaply discards duplicates and non-matching rows before heavier join machinery runs.</li>
<li><strong>Original motivation, still running:</strong> spell-checkers and hyphenation dictionaries were among the earliest uses — a huge word list compressed into RAM-sized bits, with rare false “correct” spellings as the accepted cost.</li>
</ul></div>
<div class="appcard">
<span class="tag tag-blue">Networks</span><h3>Forwarding &amp; light clients</h3>
<ul>
<li><strong>Packet forwarding:</strong> routers use Bloom filters to summarise which prefixes or subscribers sit behind an interface, compressing forwarding state that would not fit in fast memory as an exact table.</li>
<li><strong>Bitcoin light clients (BIP 37):</strong> an SPV client sends its node a Bloom filter of the addresses it cares about; the node forwards only matching transactions. The known weakness is privacy — a loosely tuned filter matches too much and leaks interest — which is itself a lesson in what p means.</li>
<li><strong>Ethereum block headers:</strong> each header carries a 2048-bit logs bloom aggregating the event-log addresses and topics in the block, so light clients can skip blocks that provably contain no log they follow.</li>
</ul></div>
</div>

<tr><th>Setting</th><th>The expensive work avoided</th><th>What a false positive costs</th><th>What a false negative would cost</th></tr>
<tr><td>LSM database lookup</td><td>Opening and searching an SSTable on disk</td><td>One wasted file check</td><td>A live key reported missing — data loss</td></tr>
<tr><td>Cache digest lookup</td><td>A query to a peer cache</td><td>One wasted peer request</td><td>A cached object treated as absent and re-fetched from origin</td></tr>

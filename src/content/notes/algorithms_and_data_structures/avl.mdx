<div class="px">
<header class="hero">
<div class="kicker">Data structures — the self-balancing search tree</div>
<p class="lede">A binary search tree is only fast while it stays bushy. Insert sorted keys into a plain BST and it quietly degenerates into a linked list: search becomes a walk down a chain of <em>n</em> nodes. The <strong>AVL tree</strong> — named for Adelson-Velsky and Landis, who described it in 1962 — refuses to let that happen. Every node stores the height of its subtree, and after each insert or delete the tree checks one number per node, the <strong>balance factor</strong>. If any factor drifts outside −1, 0, +1, a local rearrangement called a <strong>rotation</strong> restores it on the spot. The payoff is a hard guarantee, proved at the end of this page: the height can never exceed about 1.44 times the height of a perfect tree, so search, insert, and delete are logarithmic — always, not just on average.</p>
<div class="keybox"><p><strong>The one-sentence idea.</strong> Keep every node&rsquo;s two subtrees within one level of each other in height. That single local rule, repaired by rotations after every update, is enough to force the whole tree&rsquo;s height to stay within a constant factor of optimal.</p></div>
</header>
</div>

## 1 — A BST with a second promise: stay balanced

<div class="px">
<p>An AVL tree is first of all a binary search tree: for every node, all keys in its left subtree are smaller and all keys in its right subtree are larger. On top of that it adds the <strong>AVL invariant</strong>: at every node, the heights of the left and right subtrees differ by at most one. Height here counts <em>edges</em> on the longest downward path — a leaf has height 0, and an empty subtree has height −1. Each node caches its height, so checking the invariant at a node is a single subtraction.</p>

<h3>How to read this</h3>
<ul>
<li><strong>Height is cached, not recomputed.</strong> Each node stores its height; after an update, only the nodes on the path back to the root need their heights refreshed — everyone else&rsquo;s subtree did not change.</li>

<p style="margin-top:18px">Two consequences are worth internalising before moving on. First, the factor is about <em>height difference</em>, not node counts: a left subtree can hold nearly twice as many nodes as the right and still have the same height, so a factor of 0 does not mean the tree is perfectly filled. Second, because heights only change along the path of an update, a single insert or delete can push a factor from +1 to +2, but never further in one step. The repair therefore always starts from a factor of exactly ±2, and the shape of the offending subtree tells us exactly which repair applies. That shape analysis is the whole content of the next step.</p>

## 3 — Rotations: the only repair tool

<div class="px">
<p>When a node reaches factor ±2, the fix never rebuilds the subtree — it <em>rotates</em> it. A rotation is a constant-time rearrangement of two or three nodes that preserves the inorder sequence exactly, so the BST property survives untouched, while pulling the tall side down one level and lifting the short side up. Because the inorder sequence is preserved, a rotation can never break the search-tree ordering; it only redistributes height.</p>
<p>Which rotation applies depends on the <em>shape</em> of the imbalance, named by the two steps you take from the unbalanced node toward the new growth. If the growth is on the outside — left-left or right-right — the unbalanced node&rsquo;s child is already leaning the same way, and one rotation settles it. If the growth is on the inside — left-right or right-left — the child leans the <em>wrong</em> way, and a single rotation would just move the problem; the child must first be rotated to straighten the bend, then the original node is rotated. Pick a case and step through it.</p>

## 4 — Insert: descend, attach, climb back repairing

<div class="px">
<p>Insertion is an ordinary BST insert — descend comparing keys, attach the new node as a leaf — followed by a walk back up the same path. On the way up, each ancestor gets its height refreshed and its factor checked. The <em>lowest</em> ancestor that reaches ±2 is where the trouble is: one single or double rotation there restores that subtree&rsquo;s height to what it was before the insert, which automatically re-validates every ancestor above it. That is why an insert never needs more than one repair: at most two rotations, total.</p>

## 5 — Delete: three shapes of removal, then a possibly long climb

<div class="px">
<p>Deletion starts as ordinary BST deletion, which has three shapes. A <strong>leaf</strong> is simply unlinked. A node with <strong>one child</strong> is spliced out and its child takes its place. A node with <strong>two children</strong> cannot be spliced, so its key is overwritten with its <em>inorder successor</em> — the smallest key in its right subtree — and that successor, which has at most one child, is deleted instead. After the structural removal, the walk back to the root refreshes heights and factors exactly as in insert — with one crucial difference: a rotation after a delete can leave the subtree <em>shorter</em> than before, so an ancestor that was fine a moment ago can tip to ±2 as well. Repairs can <strong>cascade</strong> all the way to the root, up to one rotation per level.</p>
<p>There is also one case that only delete can produce: the child of the unbalanced node has factor 0. A single rotation still fixes it (the subtree keeps its height, so the cascade stops there). The sequence below starts from an 11-node tree and deletes 5, 70, 60, 40 — covering a leaf, another leaf, a one-child splice that forces a rotation at the root, and a two-children delete that ends in a rotation too.</p>

## 7 — Why the height stays logarithmic

<div class="px">
<p>The guarantee does not come from watching the tree grow. It comes from the opposite question: <em>what is the fewest nodes an AVL tree of a given height can possibly have?</em> If even the sparsest legal tree of height h needs exponentially many nodes, then turning the statement around, a tree with n nodes cannot be very tall — its height is forced to be logarithmic in n. So build the sparsest tree: to reach height h as cheaply as possible, the root needs one subtree of height h − 1 (to set the height) and — because the factor may not exceed 1 — the other subtree must be at least height h − 2. Making both as sparse as possible gives the recurrence, where N(h) is the minimum number of nodes in any AVL tree of height h.</p>

## 8 — Costs, comparisons, and where AVL trees earn their keep

<div class="px">
<table class="data">
<tr><th>Operation</th><th>Cost</th><th>Why</th></tr>
<tr><td>Search</td><td>O(log n)</td><td>One root-to-leaf path; the height is at most about 1.44 log<sub>2</sub> n.</td></tr>
<tr><td>Insert</td><td>O(log n)</td><td>Descend O(log n), then at most one single or double rotation on the climb.</td></tr>
<tr><td>Delete</td><td>O(log n)</td><td>Descend O(log n); repairs may cascade, but at most one rotation per level.</td></tr>
<tr><td>Rotation</td><td>O(1)</td><td>Three pointer changes and two height recomputes, independent of subtree size.</td></tr>
<tr><td>Space overhead</td><td>One height (or factor) per node</td><td>The factor fits in two bits; many implementations store it instead of the full height.</td></tr>
</table>
<p><strong>AVL versus red-black.</strong> Both guarantee logarithmic height, but they strike the balance bargain differently. AVL&rsquo;s rule is stricter — heights within one level — so its trees are a little shorter (worst case about 1.44 log<sub>2</sub> n against red-black&rsquo;s 2 log<sub>2</sub> n) and lookups a little faster. The price is paid on updates: red-black trees bound the number of rotations per insert and delete by a small constant with a looser invariant, while AVL deletes can rotate at many levels, and AVL inserts rebalance more often in practice. The usual rule of thumb follows: <em>read-heavy</em> workloads favour AVL; <em>write-heavy</em> ones favour red-black — which is why red-black trees sit inside most standard-library maps (C++ <code>std::map</code>, Java <code>TreeMap</code>), while AVL trees show up where lookup latency must be as tight and predictable as possible, and throughout textbooks, because the height-and-factor machinery is the cleanest way to see <em>why</em> balancing works at all.</p>
<p><strong>Where the pieces recur.</strong> The stored-height trick reappears in B-trees and their variants that index databases and filesystems — there the “rotation” becomes a node split or merge, but the idea is identical: keep a cheap local measure, check it on the path back up, repair locally. Learn AVL and the rest of the balanced-tree family reads as variations on one theme.</p>
<div class="keybox"><p><strong>The arc, in one breath.</strong> Store heights, subtract to get balance factors, and insist each factor stays in \{−1, 0, +1\}. Repair violations with rotations — single for straight growth, double for bent growth — on the climb back from every insert and delete. The sparsest tree obeying the rule is a Fibonacci tree, its node count grows like φ<sup>h</sup>, and so every AVL tree with n nodes has height O(log n). Balance is not maintained by luck or by rebuilding; it is maintained by arithmetic.</p></div>

function stepper(cfg){

    cfg.note.innerHTML = cfg.notes[idx];
    cfg.prev.disabled = idx === 0; cfg.next.disabled = idx === cfg.count - 1;
    if(idx === cfg.count - 1) stop();
  }
  cfg.prev.addEventListener("click", function(){ stop(); if(idx > 0) idx--; render(); });
  cfg.next.addEventListener("click", function(){ stop(); if(idx < cfg.count - 1) idx++; render(); });
  cfg.play.addEventListener("click", function(){
    if(timer){ stop(); return; }
    if(idx === cfg.count - 1) idx = 0;
    render();
    cfg.play.textContent = "Pause";
    timer = setInterval(function(){ if(idx < cfg.count - 1){ idx++; render(); } else stop(); }, 1700);
  });
  render();
  return { refresh: render, stop: stop, setData: function(count, notes){ cfg.count = count; cfg.notes = notes; idx = 0; stop(); render(); } };
}

  rots.forEach(function(r){ parts.push((r.dir === "right" ? "Right" : "Left") + " rotation at " + r.at + " lifted " + r.up + "."); });

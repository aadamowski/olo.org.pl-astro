<div class="px">
<header class="hero">
<div class="kicker">Data structures: the self-balancing search tree</div>
<p class="lede">A binary search tree stays fast only while it stays bushy, and the <strong>red-black tree</strong> is the balancing scheme that won: it sits inside C++ <code>std::map</code>, Java <code>TreeMap</code>, the Linux kernel&rsquo;s <code>rbtree</code>, and countless schedulers and indexes. Instead of the AVL tree&rsquo;s strict height arithmetic, it gives every node one extra bit — a <strong>colour</strong>, red or black — and enforces five colouring rules. Those rules are looser than AVL&rsquo;s, so updates do less restructuring, yet they still cap the longest root-to-leaf path at twice the shortest, and that single fact forces the height to stay logarithmic. This page builds the whole mechanism: the five invariants, the two repair moves (rotation and recolouring), every insert and delete fix-up case, and the proof at the end.</p>
<div class="keybox"><p><strong>The one-sentence idea.</strong> Colour every node red or black so that no path from a node down to a leaf ever contains more black nodes than any other path from that node — then no path can be more than twice as long as another, and the tree can never degenerate into a chain.</p></div>
</header>
</div>

## 1 — The five invariants

<div class="px">
<p>A red-black tree is a binary search tree in which every node carries a colour, and the colours obey five rules. Four of them are about red; the fifth is the one that does the real work. To make the rules airtight, every missing child is drawn as a special leaf called a <strong>NIL node</strong>: it holds no key, counts as black, and terminates every path. Counting NILs is what lets rule 5 compare paths of different shapes fairly.</p>
<table class="formulas">
<tr><th>Rule 1: Every node is coloured</th><td>Each node is exactly one of red or black. The colour is one bit of storage per node.</td></tr>
<tr><th>Rule 2: The root is black</th><td>No exceptions, even for a one-node tree. Fix-up routines may temporarily redden the root; they always blacken it again before finishing.</td></tr>
<tr><th>Rule 3: Every NIL leaf is black</th><td>All NIL nodes share one colour by definition: black. They are the leaves every path ends at.</td></tr>
<tr><th>Rule 4: Red nodes have black children</th><td>A red node&rsquo;s children — real or NIL — are both black. Equivalently: no red node ever has a red parent, so reds are always separated by at least one black. This is the rule insertions most often break, and the one every insert fix-up case is about.</td></tr>
<tr><th>Rule 5: Equal black counts on every path</th><td>For every node, all simple paths from that node down to NIL leaves contain the same number of black nodes. The shared count is called the node&rsquo;s <strong>black-height</strong>:</td></tr>
</table>

<div class="readbox">
<h3>How to read this</h3>
<ul>
<li><strong>Rule 5 is the guarantee; rules 2–4 protect it.</strong> Equal black counts alone would still permit a chain of red nodes stretching one path. Rule 4 caps how many reds can pad a path: at most one red between consecutive blacks.</li>
<li><strong>New nodes are born red.</strong> A red leaf cannot break rule 5 (it adds no black), so an insert can only ever break rule 4, or rule 2, if it becomes the root. Fix-up is correspondingly narrow.</li>
<li><strong>NILs are usually one shared sentinel.</strong> Real implementations allocate a single black NIL object and point every empty child at it, so rule 3 costs no memory per leaf.</li>
</ul></div>

## 2 — The only two moves: rotation and recolouring

<div class="px">
<p>Every fix-up in this page is assembled from exactly two moves. A <strong>rotation</strong> is the same constant-time pointer rearrangement as in a plain BST: a node and its child swap levels, the child&rsquo;s inner subtree (labelled β below) is handed across, and the inorder sequence — hence the BST property — is preserved exactly. A rotation changes no colours by itself. A <strong>recolouring</strong> is the opposite extreme: it changes no pointers at all, only colour bits, so it cannot disturb the BST property or the tree&rsquo;s shape — it can only move black-height between paths, which is exactly what several fix-up cases need.</p>
<p>Step through a left rotation below. The pivot is 10, its right child 20 rises, and β (the inner subtree, everything between 10 and 20 in key order) is handed down to become 10&rsquo;s right subtree. The right rotation is the mirror image; the buttons switch between them.</p>

## 3 — Insert fix-up: three cases, told by the uncle

<div class="px">
<p>Insertion is an ordinary BST insert with the new node coloured <strong>red</strong>. As Step 1 noted, a red leaf adds no black to any path, so rule 5 survives automatically; the only possible damage is a <strong>red-red edge</strong> — the new node&rsquo;s parent is also red, breaking rule 4, or a red root, breaking rule 2. Fix-up walks upward from the new node repairing red-red edges, and which case applies at each level is decided by one node: the <strong>uncle</strong>, the grandparent&rsquo;s other child.</p>
<table class="formulas">
<tr><th>Case 1: Uncle is red</th><td>Recolour only: parent and uncle go black, grandparent goes red. The red-red edge is gone at this level, but the grandparent is now red, so the problem may reappear two levels up. Repeat from the grandparent. No rotation, and the subtree&rsquo;s black-height is unchanged — the two new blacks below exactly balance the grandparent&rsquo;s lost black on every path through it.</td></tr>
<tr><th>Case 2: Uncle is black, new node is an inner grandchild</th><td>The new node sits on the <em>inside</em> — a right child of a left child, or the mirror. Rotate the parent away from the grandparent: the new node rises into the parent&rsquo;s place and the shape becomes the straight line of Case 3. Nothing is fixed yet; this case only converts.</td></tr>
<tr><th>Case 3: Uncle is black, new node is an outer grandchild</th><td>The growth is a straight line. Rotate the grandparent toward the short side, then recolour: the risen parent goes black, the grandparent goes red. The red-red edge is gone, black-height is preserved, and fix-up ends — this case always terminates the loop.</td></tr>
</table>
<p>Pick a case and step through it. Each walkthrough starts from a valid tree, inserts one red node, and repairs what breaks. A NIL uncle counts as black, which is why Case 3 below needs no visible uncle at all.</p>

## 4 — Delete fix-up: the doubly-black node and four cases

<div class="px">
<p>Deletion is where red-black trees earn their reputation for subtlety. Removing a <strong>red</strong> node is free: it sits on no path&rsquo;s black count and has black children, so splicing it out breaks nothing. Removing a <strong>black</strong> node is different — every path through it loses one black, and rule 5 breaks. The standard bookkeeping trick is to pretend the node that slides into the deleted node&rsquo;s place inherits the lost black as an <em>extra</em> black: it becomes <strong>doubly black</strong>. A doubly-black node is drawn below as a black square marked DB. If it is a real red node it becomes “red-and-black” and simply ends black; the interesting situation is a doubly-black NIL, which is what all four cases below start from. Fix-up&rsquo;s whole job is to shed that extra black — by pushing it up, or by borrowing black-height from the sibling&rsquo;s subtree through a rotation.</p>
<p>Which case applies is decided by the <strong>sibling</strong> of the doubly-black node and the colours of the sibling&rsquo;s children (its nephews). The four cases, for a doubly-black node on the left (mirror everything if it is on the right):</p>
<table class="formulas">
<tr><th>Case 1: Sibling is red</th><td>Recolour the sibling black and the parent red, then rotate the parent toward the doubly-black side. <h3>Why delete is harder than insert</h3>
<ul>
<li><strong>The deficit can climb the whole tree.</strong> Insert&rsquo;s red-red edge is a local surplus that recolouring pushes up two levels at a time; delete&rsquo;s missing black is a deficit that Case 2 pushes up one level at a time, potentially to the root — where it harmlessly evaporates, because the root&rsquo;s extra black can simply be dropped.</li>
<li><strong>Two children means a successor swap first.</strong> Deleting a node with two children copies its inorder successor&rsquo;s key into it and deletes the successor instead — and the successor, having no left child, is always one of the easy shapes. The colour that matters for fix-up is the successor&rsquo;s original colour.</li>
<li><strong>Rotations are rarer than recolourings.</strong> Across a whole delete there are at most three rotations; everything else is colour flips on the climb. This is the concrete sense in which red-black updates are cheaper than AVL&rsquo;s.</li>
</ul></div>

## 6 — Why the height stays logarithmic

<div class="px">
<p>The proof has two halves, and both come straight from the invariants. First, rule 5 forces any tree with a given black-height to contain <em>exponentially</em> many nodes: a subtree whose paths all carry <em>bh</em> blacks cannot be a scrawny chain, it must branch enough to hold at least 2<sup><em>bh</em></sup> − 1 nodes. Second, rule 4 caps how much taller than the black-height the tree can be: reds can pad a path, but never two in a row, so at least half the nodes on any root-to-leaf path are black and the height is at most twice the black-height. Chain the two halves together and the height is at most twice a logarithm.</p>

## 7 — Costs, comparisons, and where red-black trees earn their keep

<div class="px">
<table class="data">
<tr><th>Operation</th><th>Cost</th><th>Why</th></tr>
<tr><td>Search</td><td>O(log n)</td><td>One root-to-leaf path; height at most 2 log<sub>2</sub>(n + 1) by Step 6.</td></tr>
<tr><td>Insert</td><td>O(log n)</td><td>Descend O(log n); fix-up recolours on the climb and rotates at most twice.</td></tr>
<tr><td>Delete</td><td>O(log n)</td><td>Descend O(log n); fix-up climbs with recolourings and rotates at most three times.</td></tr>
<tr><td>Rotation</td><td>O(1)</td><td>Three pointer changes, independent of subtree size.</td></tr>
<tr><td>Recolouring</td><td>O(1)</td><td>Colour-bit flips only; no pointers move.</td></tr>
<tr><td>Space overhead</td><td>One bit per node</td><td>The colour. Often packed into a spare bit of a pointer or a flags word, so the real overhead can be zero bytes.</td></tr>
</table>
<p><strong>Red-black versus AVL.</strong> Both guarantee logarithmic height; they strike the bargain at different points. AVL&rsquo;s rule — subtree heights within one — is stricter, so AVL trees are a little shorter (worst case about 1.44 log<sub>2</sub> n against red-black&rsquo;s 2 log<sub>2</sub> n) and pure lookups a little faster. Red-black&rsquo;s looser colour rules buy cheaper updates: bounded rotations per operation (at most two for insert, three for delete), with most fix-up work done by recolouring, and no heights to maintain — one bit instead of a stored height or factor per node. The usual rule of thumb follows: <em>read-heavy</em> workloads favour AVL; <em>write-heavy</em> ones favour red-black. Practice agrees: red-black trees are the default ordered map in C++ (<code>std::map</code>) and Java (<code>TreeMap</code>), the Linux kernel&rsquo;s intrusive <code>rbtree</code> orders everything from virtual memory areas to timers, and database and filesystem code reaches for them whenever a balanced ordered structure must survive heavy mutation.</p>
<p><strong>Where the pieces recur.</strong> The doubly-black bookkeeping is the same deficit-tracking idea as the borrow in subtraction, and the “recolour first, rotate only when forced” pattern recurs in AA trees (a red-black variant where reds lean one way), left-leaning red-black trees (the form Sedgewick popularised, used in several standard libraries), and the balancing of B-tree nodes on disk, where a “rotation” is a page split and recolouring&rsquo;s role is played by separator-key changes.</p>
<div class="keybox"><p><strong>The arc, in one breath.</strong> Colour every node red or black, keep the root and the NIL leaves black, never let a red node touch another red, and insist every downward path carries the same number of blacks. Insert red and repair red-red edges by asking about the uncle — recolour if he is red, rotate if he is black. Delete black and track the missing black as a doubly-black node, repairing by asking about the sibling and its nephews. And because equal black counts force exponential size while reds at most double a path, the height is at most twice a logarithm — balance maintained not by rebuilding, but by bookkeeping.</p></div>

function tagIds(root, prefix){
  /* assign stable _id = prefix + value (values unique within each snapshot) */
  (function w(n){ if(!n) return; if(typeof n.v==="number") n._id = prefix+n.v; if(n.db) n._id = prefix+"DB"; if(n.tri) n._id = prefix+n.tri; w(n.l); w(n.r); })(root);

}
function stepper(cfg){
  var idx = 0, timer = null;
  function stop(){ if(timer){ clearInterval(timer); timer=null; cfg.play.textContent="Play"; } }
  function render(){
    cfg.render(idx);
    cfg.prog.textContent = "Step "+(idx+1)+" of "+cfg.count;
    cfg.note.innerHTML = cfg.notes[idx];
    cfg.prev.disabled = idx===0; cfg.next.disabled = idx===cfg.count-1;
    if(idx===cfg.count-1) stop();
  }
  cfg.prev.addEventListener("click", function(){ stop(); if(idx>0) idx--; render(); });
  cfg.next.addEventListener("click", function(){ stop(); if(idx<cfg.count-1) idx++; render(); });
  cfg.play.addEventListener("click", function(){
    if(timer){ stop(); return; }
    if(idx===cfg.count-1) idx=0;
    render(); cfg.play.textContent="Pause";
    timer = setInterval(function(){ if(idx<cfg.count-1){ idx++; render(); } else stop(); }, 1800);
  });
  render();
  return { refresh: render, stop: stop,
    setData: function(count, notes, renderFn){ cfg.count=count; cfg.notes=notes; if(renderFn) cfg.render=renderFn; idx=0; stop(); render(); } };
}

function pathBH(root, v){
  /* walk root->v, then count blacks below v on a path to NIL */
  var n = root, chain = [];
  while(n && n.v!==v){ chain.push(n); n = v < n.v ? n.l : n.r; }
  if(!n) return null;
  return bhOf(n);
}
function auditTree(root){
  /* returns checks: {bst, rootBlack, nilBlack, noRedRed, equalBH} plus details */
  var res = {bst:true, rootBlack: root.c==="B", nilBlack:true, noRedRed:true, equalBH:true, badBHNode:null, redRedAt:null};
  var prev = -Infinity;
  (function ino(n){ if(!n||n.nil) return; ino(n.l); if(n.v<=prev) res.bst=false; prev=n.v; ino(n.r); })(root);
  (function w(n){
    if(!n || n.nil) return;
    if(n.c==="R"){
      [n.l,n.r].forEach(function(c){ if(c && !c.nil && c.c==="R"){ res.noRedRed=false; if(!res.redRedAt) res.redRedAt=n.v; } });
    }
    w(n.l); w(n.r);
  })(root);
  (function bh(n){
    if(!n || n.nil) return 1;
    var l = bh(n.l), r = bh(n.r);
    if(l<0 || r<0) return -1;
    if(l!==r){ if(!res.badBHNode) res.badBHNode=n.v; res.equalBH=false; return -1; }
    return l + (n.c==="B"?1:0);
  })(root);
  return res;
}

function pgDelete(v){
  EV5 = [];
  var z = pgRoot;
  while(z !== NIL5 && z.v !== v) z = v < z.v ? z.l : z.r;
  if(z === NIL5){ EV5.push({t:"missing", v:v}); return false; }
  var y = z, yOrig = y.c, x;
  if(z.l === NIL5){ x = z.r; pgTransplant(z, z.r); }
  else if(z.r === NIL5){ x = z.l; pgTransplant(z, z.l); }
  else {
    y = pgMin(z.r); yOrig = y.c; x = y.r;
    EV5.push({t:"succ", from:v, to:y.v});

    pgTransplant(z, y); y.l = z.l; y.l.p = y; y.c = z.c;

function pgAudit(){
  if(pgRoot === NIL5) return {ok:true};

  (function bh(n){
    if(n === NIL5) return 1;

    var l = bh(n.l), r = bh(n.r);

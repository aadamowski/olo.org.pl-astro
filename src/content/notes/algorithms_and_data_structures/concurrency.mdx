<div class="px">
<header class="hero">
<div class="kicker">Algorithms — running many things at once</div>
<p class="lede">A single-threaded program has one story: each line runs, then the next. Add a second thread and the stories interleave — and almost every classic bug in concurrent code is a bad interleaving. Two increments can lose one update. Two threads can each wait forever for the other. A polite program can dance forever without moving. A low-priority thread can hold up the most important task in the system. This page builds each failure live, in a stepper or simulator you control, then applies the standard fix in the same picture: <strong>mutexes</strong>, <strong>lock ordering</strong>, <strong>fair queues</strong>, <strong>randomised backoff</strong>, <strong>priority inheritance</strong>, <strong>semaphores</strong>, and <strong>lock-free compare-and-swap</strong>.</p>
<div class="keybox"><p><strong>The one-sentence idea.</strong> Concurrency bugs are rarely about a wrong line of code — they are about a <em>schedule</em> you did not imagine, so every fix works by removing bad schedules: serialising a critical section, ordering lock acquisition, bounding waits, breaking symmetry, or making an update atomic so no schedule can split it.</p></div>
</header>
</div>

## 1 — The dining philosophers: every problem at one table

<div class="px">
<p>Edsger Dijkstra posed this problem in 1965 (Tony Hoare later gave it its familiar form) to make the dangers of shared resources impossible to ignore. Five philosophers sit around a round table. Each alternates between <strong>thinking</strong> and <strong>eating</strong>. In the centre is a bowl of rice; between each pair of neighbours lies a single fork — five forks in total. To eat, a philosopher needs <em>both</em> forks beside their plate: the one on their left and the one on their right. A fork can be held by only one philosopher at a time. When finished eating, a philosopher puts both forks down and goes back to thinking.</p>
<p>Read the table as code and it is the whole of this page in miniature. A philosopher is a <strong>thread</strong>. A fork is a <strong>lock</strong> guarding a shared resource. Eating is a <strong>critical section</strong> that needs two locks at once. Thinking is work that needs no locks at all. The obvious protocol — <em>pick up your left fork, then pick up your right fork, eat, put both down</em> — looks harmless for one philosopher. Run five copies at once and a schedule exists in which nobody ever eats again.</p>
<table class="formulas">
<tr><th>The cast, translated</th><td><strong>Philosopher</strong> → thread or process. <strong>Fork</strong> → lock / shared resource (mutual exclusion: one holder at a time). <strong>Needs both forks to eat</strong> → a critical section that must hold two locks at once. <strong>Waiting with one fork in hand</strong> → hold-and-wait, one of the four Coffman conditions for deadlock in Step 3.</td></tr>
<tr><th>The naive protocol</th><td><code>think(); take(left fork); take(right fork); eat(); put down both forks;</code>, with <code>take()</code> blocking until the fork is free. Every philosopher runs exactly this code, in exactly this order.</td></tr>
<tr><th>What can go wrong</th><td><strong>Deadlock</strong> if all five pick up their left fork at once: each holds one fork and waits forever for a neighbour&rsquo;s fork. The same table can also show <strong>starvation</strong> (a philosopher whose neighbours keep alternating so one fork is always taken). That is why a correct solution must guarantee not just that <em>someone</em> can eat, but that <em>everyone</em> eventually does.</td></tr>
</table>
<p>Step through the naive protocol below and watch the wait cycle close — each philosopher waiting on the next, all the way around the table and back to the start. Then tick the fix and step again. The fix changes only one philosopher&rsquo;s code: <strong>Philosopher 5 picks up forks in the opposite order</strong> (right fork first). That single asymmetry means Philosopher 5 and Philosopher 1 contend for the <em>same</em> first fork, so one of them starts empty-handed instead of holding a fork hostage — the circle can never close, and the meal works its way around the table.</p>

<h3>Why this one problem previews the whole page</h3>
<ul>
<li><strong>Deadlock (Step 3)</strong> is the closed ring of waiting below: all four Coffman conditions hold at once — forks are exclusive, philosophers hold-and-wait, forks cannot be preempted, and the wait is circular.</li>
<li><strong>The fix is lock ordering in disguise (Step 3 again).</strong> Reversing one philosopher&rsquo;s pickup order is the dining-table version of a resource hierarchy: it breaks circular wait, the one Coffman condition that ordering can remove.</li>
<li><strong>Other classic fixes exist.</strong> A <em>waiter</em> (arbitrator) who seats at most four philosophers at once guarantees at least one diner can always get both forks. Letting a philosopher pick up both forks only if <em>both</em> are free (and putting the first back otherwise) removes hold-and-wait. Each fix buys progress by removing a different Coffman condition.</li>
<li><strong>Deadlock-free is not starvation-free.</strong> The asymmetric protocol below cannot deadlock, but an unlucky philosopher can still be repeatedly beaten to a fork — the fairness problem of Step 4 needs its own guarantee on top.</li>
</ul></div>

## 2 — Race conditions: the lost update

<div class="px">
<p>A <strong>race condition</strong> is any bug whose presence depends on the relative timing of threads. The canonical example fits in three lines. Incrementing a shared counter looks like one operation, but the machine does it in three: <em>read</em> the value into a register, <em>add</em> one, <em>write</em> it back. If two threads interleave inside that window, both read the same starting value, both write the same result — and one increment simply vanishes. No line is wrong. The schedule is wrong.</p>
<pre class="code"><span class="cm">// executed by both threads, counter starts at 0</span>&#10;reg = counter;   <span class="cm">// READ</span>&#10;reg = reg + 1;   <span class="cm">// ADD</span>&#10;counter = reg;   <span class="cm">// WRITE</span></pre>
<p>Step through the bad schedule below. Then tick <strong>protect with a mutex</strong> and step again: the same three lines now run inside a critical section, the second thread is forced to wait at the door, and both increments land. Figure titles track the schedule as you step.</p>

<h3>Why this generalises</h3>
<ul>
<li><strong>Check-then-act</strong> is the same shape: <code>if (x == null) x = make()</code> races when two threads both pass the check.</li>
<li><strong>The window is tiny but real.</strong> A context switch can land between any two machine instructions, so &ldquo;it never happens in testing&rdquo; means only that the bad schedule is rare.</li>
<li><strong>A data race is worse than a wrong answer.</strong> In C and C++ a data race is undefined behaviour; in Java it can tear a 64-bit write into two 32-bit halves. The fix is never &ldquo;hope&rdquo; — it is synchronisation or an atomic.</li>
</ul></div>

## 3 — Mutexes: the fix, and its price

<div class="px">
<p>A <strong>mutex</strong> (mutual exclusion lock) admits exactly one thread into a <strong>critical section</strong> at a time. Everyone else blocks at <code>lock()</code> until <code>unlock()</code>. That one guarantee — the three-line increment can no longer be split — is what repaired Figure 1. But serialising has a price: the critical section is, by definition, work that cannot be parallelised, and it caps your speedup no matter how many cores you buy. That cap is <strong>Amdahl&rsquo;s law</strong>.</p>

## 4 — Deadlock: the circular wait

<div class="px">
<p>A <strong>deadlock</strong> is a set of threads each waiting for a resource held by the next, in a cycle, forever. Nobody is running, nobody will ever run, and no timeout inside the threads themselves can fire because no thread is executing. Coffman&rsquo;s four conditions are each <em>necessary</em> — break any one and deadlock is impossible:</p>

<tr><th>1. Mutual exclusion</th><td>A resource can be held by only one thread at a time. (Hard to remove; it is usually the point of the lock.)</td></tr>
<tr><th>2. Hold and wait</th><td>A thread holds one resource while waiting for another. Removed by acquiring all locks at once, or by try-lock-and-release.</td></tr>
<tr><th>3. No preemption</th><td>A held resource cannot be forcibly taken away; only the holder releases it.</td></tr>
<tr><th>4. Circular wait</th><td>A cycle exists in the wait-for graph. Removed by a <strong>global lock order</strong>: every thread acquires locks in the same agreed order, so a cycle can never close.</td></tr>
</table>

</ul></div>

## 5 — Starvation: runnable, but never chosen

<div class="px">
<p><strong>Starvation</strong> is quieter than deadlock: the system as a whole makes progress, most threads make progress — but one thread is perpetually passed over. A reader–writer lock that always prefers readers can starve a single writer under a steady stream of readers. An unfair mutex can re-grant the lock to the thread that just released it, because it is still hot in cache, while a waiting thread never gets scheduled onto the lock at all.</p>
<p>The simulator below runs 30 scheduling quanta shared by two &ldquo;hog&rdquo; threads and one low-demand thread, Low. Drag the scheduler&rsquo;s bias toward the hogs and watch Low&rsquo;s bar shrink to nothing — that is starvation, no cycle and no bug in Low&rsquo;s code. Then tick the fair FIFO queue: the lock (and the CPU) is granted strictly in arrival order, Low is guaranteed a turn within two quanta, and starvation is impossible by construction.</p>

## 6 — Livelock: busy, polite, and stuck

<div class="px">
<p>In a <strong>livelock</strong> nobody is blocked — that is what makes it insidious. Two threads keep <em>reacting</em> to each other, changing state constantly, burning CPU, and making zero progress. The everyday picture is two people in a corridor who both step left, then both step right, then both step left, forever. Code does the same thing when two threads each politely release a lock and retry in perfect lockstep, or when two network nodes retransmit in synchronised bursts after every collision.</p>
<p>Step through the corridor dance: the attempt counter climbs, the progress bar never moves. Then tick <strong>randomised backoff</strong> — each robot waits a <em>random</em> delay before retrying — and step again. Randomness breaks the symmetry: one robot happens to wait longer, the other walks through, and the system escapes. This is precisely why Ethernet, Wi-Fi, and TCP all back off exponentially <em>and randomly</em> after a collision.</p>

## 7 — Priority inversion: the important thread waits on the wrong one

<div class="px">
<p>Real-time systems rank threads by priority and always run the highest-priority runnable thread. Now suppose the <em>low</em>-priority thread L holds a lock, and the <em>high</em>-priority thread H wakes and needs that lock. H blocks — correctly — waiting for L. But a <em>medium</em>-priority thread M, which needs nothing, is now the highest-priority <em>runnable</em> thread, so it preempts L. L cannot finish its critical section, so H cannot run. H, the most important thread in the system, is effectively waiting on M — a thread it outranks and that has nothing to do with the lock. Priority has been <strong>inverted</strong>, for as long as medium-priority work keeps arriving: potentially forever.</p>
<div class="callout"><p><strong>This bug nearly ended a Mars mission.</strong> In July 1997 the Mars Pathfinder lander began resetting itself, losing data, a few days after landing. Engineers traced it to exactly this pattern in the VxWorks real-time OS: a low-priority data-gathering task held a bus mutex, a high-priority bus task blocked on it, and medium-priority communications tasks kept preempting the low one. The fix, uploaded to Mars, was to turn on priority inheritance for that mutex.</p></div>
<p>Drag the time slider. Without inheritance, watch M&rsquo;s long run push H&rsquo;s start out to <math><mi>t</mi><mo>=</mo><mn>10</mn></math>. Then tick <strong>priority inheritance</strong>: while H waits, L temporarily <em>inherits</em> H&rsquo;s priority, M can no longer preempt it, L finishes at <math><mi>t</mi><mo>=</mo><mn>5</mn></math>, and H&rsquo;s wait shrinks from 8 time units to 3. Inheritance does not make H wait-free — it bounds H&rsquo;s wait by one critical section, which is the best any lock can promise.</p>

<li><strong>Remove the lock:</strong> hand data between priority levels through a lock-free queue (Step 8) so the high-priority thread never blocks at all.</li>
<li><strong>What inheritance does not fix:</strong> chained blocking (H waits on L, who waits on a lock held by someone else) still adds up — inheritance propagates along the chain, but each critical section still costs time.</li>
</ul></div>

## 8 — Semaphores: counting permits, and the bounded buffer

<div class="px">
<p>A mutex answers &ldquo;may I enter?&rdquo; with yes or no. A <strong>semaphore</strong> (Dijkstra) keeps a <em>count</em> of permits. <code>wait()</code> (historically <code>P()</code>) decrements the count, blocking if it would go negative. <code>signal()</code> (<code>V()</code>) increments it, waking a waiter. A mutex is the special case where the count starts at 1; a semaphore starting at <math><mi>N</mi></math> admits up to <math><mi>N</mi></math> concurrent users of a pooled resource.</p>
<p>Two semaphores plus one mutex solve the classic <strong>bounded buffer</strong> (producer–consumer) problem with no busy-waiting anywhere: <code>empty</code> counts free slots (starts at capacity), <code>full</code> counts ready items (starts at 0), and the mutex protects the slot array itself for the brief moment of putting or taking. Step through a produce/consume cycle and watch the invariant that makes it correct:</p>
<table class="formulas">
<tr><th>The invariant: checked at every step</th><td><math display="block"><mrow><mi>empty</mi><mo>+</mo><mi>full</mi><mo>=</mo><mtext>capacity</mtext></mrow></math><math display="block"><mrow><mn>3</mn><mo>+</mo><mn>0</mn><mo>=</mo><mn>3</mn><mspace width="1em"/><mtext>at the start (Figure 7, step 0)</mtext></mrow></math><math display="block"><mrow><mn>1</mn><mo>+</mo><mn>2</mn><mo>=</mo><mn>3</mn><mspace width="1em"/><mtext>at the fullest point below (step 3)</mtext></mrow></math></td></tr>
<tr><th>The protocol</th><td>Producer: <code>wait(empty)</code>, then <code>lock(mutex)</code>, put item, <code>unlock(mutex)</code>, then <code>signal(full)</code>. Consumer mirrors it with <code>wait(full)</code> and <code>signal(empty)</code>. Ordering matters: acquiring the mutex <em>before</em> the counting semaphore can deadlock: a thread could hold the mutex while blocked on <code>empty</code>, while the consumer who would free a slot needs that same mutex.</td></tr>
</table>

## 9 — Lock-free tools: compare-and-swap and the retry loop

<div class="px">
<p>Every fix so far still <em>blocks</em> someone. Lock-free programming takes the other path: never hold anything, so nobody can be blocked, deadlocked, or inverted. The workhorse is one atomic hardware instruction, <strong>compare-and-swap</strong> (CAS): &ldquo;if the value at this address still equals what I expect, replace it with my new value and tell me; otherwise just tell me.&rdquo; Read, compute, CAS — and if the CAS fails, someone else won the race, so re-read and retry. The losing thread wastes a spin, but the <em>system</em> always progresses: a failed CAS is proof another thread succeeded. That is the definition of <strong>lock-free</strong>.</p>
<pre class="code"><span class="cm">// lock-free increment: no lock taken, ever</span>&#10;do \{&#10;&nbsp;&nbsp;old = counter;          <span class="cm">// read</span>&#10;\} while (!CAS(&amp;counter, old, old + 1));  <span class="cm">// retry until our swap lands</span></pre>

<div class="px">
<p>Every problem above is a bad schedule, and every fix removes a class of schedules. This table is the page on one screen — problem, signature symptom, root cause, and the fix (or fixes) that actually address the cause.</p>
